# 玩法扩展设计（2026-10-15）

> **【2026-10-16 更新】** M1-M7 已全部落地，本文第三、五节作废；特别是第五节末尾
> 「扩到 150 关（窄高盘 8×5 / 10×6）」这条建议——那批关正是这次难度退坡的发生地。
> 关卡体系的现行设计见 **`docs/关卡最终设计.md`**（唯一真源）。第一、二节（数据放哪、机制清单）仍然有效。

> 前提：所有机制都必须保住「**每关存在可清台证书**」这条硬约束——生成器 `certify()` 会用真实
> `transition()` 重放一遍解法，证书过不了就换布局。所以机制的取舍标准是：
> **能不能被确定性重放**。会引入随机/不可预测状态的机制（游走障碍、传送门）代价最高，先不做。

## 一、关卡数据存在哪（回答你的问题）

**不是 JSON，是 TypeScript 源文件**：`cocos/assets/scripts/core/levels.ts`，100 条字面量数组，
每关一行 + 一行注释（尺寸 / 牌位 / 花色 / 冰对 / 参考解步数）。

为什么用 TS 而不是 JSON：
1. `core/` 是**双端共享**的（h5 demo 直接 import，cocos 侧编译进包），JSON 需要额外一次异步加载才能开第一帧；
2. TS 有类型（`LevelDef`）——`ice`/`flowers` 这类新字段漏写会直接编译报错，JSON 不会；
3. 生成器 `tools/author-levels.cjs` 本来就是**写回这个文件**的（带注释，方便人看）；
4. 小游戏包里读 JSON 还要多一份资源与分包配置。

如果你要「能外部编辑的关卡文件」，推荐**加一个导出**而不是换存储：
`npm run author:levels` 时顺带导出 `docs/levels.json`（只读快照，便于审阅/对比），
真源仍是 TS + 生成器（否则手改 JSON 会绕过「可清台」校验，出一堆死局关）。

## 二、现有机制清单（已实现）

空洞、木桩、双层、三层、锁行、锁列、冰面（碎冰两次）、花牌（第 51 关起入池）。
难度标量：花色数 4→27、打乱步数 2→56、盘面 3×4→8×9。详见 `docs/关卡玩法梳理.md`。

## 三、新增玩法设计（按「价值 / 成本」排序）

### M1 限步关（成本 S，价值 高）
- **玩法**：本关有步数上限，用尽仍未清台即失败。最经典的关卡差异化手段。
- **数据**：`LevelDef.moveLimit?: number`（缺省 = 不限步）。
- **改动**：Rules 不动；`Session.apply` 在 `moves++` 后判定 `moveLimit && moves>=moveLimit && count>0`
  → 新增 `modal='lose'`；失败弹窗视图已有（现在的 lose 弹窗复用）。
- **生成**：`author-levels` 用证书长度推导 `moveLimit = ceil(par * 1.5)`，并断言 `moveLimit >= par`。
- **首现**：第 30 关起，每 3-5 关来一次；后期可以收紧系数（1.5 → 1.25）。

### M2 单向轨（成本 S-M，价值 中）
- **玩法**：某条轨只能朝一个方向推（只向右 / 只向下），轨端画箭头。增加规划感，比「整条锁死」柔和。
- **数据**：`LevelDef.oneWay?: {axis:'row'|'col'; index:number; dir:1|-1}[]`。
- **改动**：`Rules.runsFor` 产出 run 时带 `dir` 约束；`rotate`/`searchHint`/拖动都按方向过滤
  （反向滑动视为无效，走现在的「推不动」提示）；视图给该轨画箭头 + 淡色底条。
- **生成**：与 lockR/lockC 互斥（同一条轨不能既锁又单向），工具里加互斥断言。
- **首现**：第 35 关起。

### M3 厚冰（成本 S，价值 中）
- **玩法**：冰牌要碎**两次**冰才露出原牌（合计三次消除）。复用现有冰机制，只是层数。
- **数据**：face 后缀加一层 `~~`（如 `5s~~`），或 `ice` 字段扩成 `{pairs, layers}`。
- **改动**：`Rules.stripIce` 只剥一层（已是如此，天然支持多层）；视图霜层画厚一点（双圈）。
- **首现**：第 70 关起，少量。

### M4 目标牌种（成本 M，价值 高）
- **玩法**：「订单」：必须消掉指定牌种/指定数量的冰牌才通关（剩余牌不计）。让关卡有明确目标而非「清空」。
- **数据**：`LevelDef.goal?: {face?: string; kind?: 'ice'|'stack'; count: number}`。
- **改动**：`Session` 统计消除记录里的目标进度（`lastErased` 已带 face/kind 信息，扩一下）；
  顶栏把「剩余 X 张」换成「目标 3/8」；win 条件改为达成目标。
- **生成**：用证书重放统计目标可达成的最大数，取 60-80% 作为 count（保证可达且有压力）。
- **首现**：第 45 关起，与限步关交替出现。

### M5 炸弹牌（成本 M，价值 中-高）
- **玩法**：`B` 牌配对成功时，额外炸掉两格的四邻（连消爽感）。
- **改动**：`Rules.transition` 的消除分支加「清邻」；certify 重放天然支持（确定性）。
- **风险**：会显著减少牌数 → 证书变短，需要工具里复算 par。
- **首现**：第 60 关起，作为「解围」牌少量出现。

### M6 花牌当百搭（成本 M-H，价值 高）
- **玩法**：花牌不与花牌配对，而是**与任意牌配对**（2 张花牌 = 两次万能配对）。让花牌从「多一种花色」变成战略资源。
- **改动**：`Rules.partners/pairs` 支持 wild；`transition` 配对时消耗 wild；
  **难点在生成器**：wild 是单张（不成对），证书重放要能选择「wild 吃哪张牌」——需要 certify 里加一层选择逻辑。
- **风险**：wild 大幅降低难度，只能在少数关出现且数量固定为 2。
- **首现**：第 55 关起，每 10 关一次。

### M7 连锁解锁（成本 M-H，价值 高）
- **玩法**：锁轨标注「先消掉 K 对才解锁」，解锁后该轨可以推。关卡有「节奏弧线」：先拆锁，再推牌。
- **改动**：`runsFor` 目前是**静态锁**，要改成「按已消对数动态计算 runs」；`Session` 维护 clearedPairs；
  certify 重放必须按同一顺序触发解锁（把解锁当作重放中的确定性事件）。
- **首现**：第 80 关起，作为终盘机制。

### 明确不做（成本过高 / 破坏确定性）
- 游走障碍、传送门、翻转牌：会让 certify 的重放失效或需要大规模改规则引擎。

## 四、配套：机制配额与验证

每加一个机制，`author-levels.cjs` 都要同步加三件事，否则会生成「名义上有、实际没用上」的关：
1. **首现关卡**与**出现频率**（例：`moveLimit` 从第 30 关起每 4 关一次）；
2. **该关确实用到了机制**的断言（例：限步关的 `moveLimit < par * 2`；目标关的目标在证书里达成）；
3. **互斥/兼容**规则（例：单向轨不能与锁轨重叠；炸弹关的 par 需复算）。

## 五、建议落地顺序

| 批次 | 内容 | 关卡变化 |
| --- | --- | --- |
| 第 1 批 | M1 限步 + M2 单向轨 + M3 厚冰 | 30 关起开始穿插，先不动总关数 |
| 第 2 批 | M4 目标牌种 + M5 炸弹 | 45 关起与限步交替 |
| 第 3 批 | M6 花牌百搭 + M7 连锁解锁 | 55/80 关起，终盘机制 |
| 之后 | 扩到 150 关（窄高盘 8×5 / 10×6 + 上述机制组合） | 需要进度页星图分页 |

先把机制做出来、在现有 100 关里穿插验证，再决定扩到多少关——这样扩关时才有真东西可编排。
